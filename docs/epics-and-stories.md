## Epic 1: הקמה ואילוצי מערכת

**יעד:** תשתית מאובטחת — שפה, מובייל, אימות משתמשים, הרשאות, קישורים חד-פעמיים, Audit Log, הצפנה, גיבוי, scaffold פרויקט ו-schema ראשוני — מוכנה ומאומתת לפני פיתוח כל יכולת משתמש.

**היקף MVP:** מלא | **NFRs:** NFR1–NFR13

**Stack טכני (לפי ארכיטקטורה v1.0):**
- Frontend: React + TypeScript + Vite + Tailwind CSS + shadcn/ui
- Routing: React Router v6
- Backend: Supabase Edge Functions
- DB: PostgreSQL (Supabase) עם Row Level Security
- Storage: Supabase Storage
- Deploy: Vercel (UI) + Supabase Cloud (backend)
- CI/CD: GitHub Actions + Vercel
- Environments: `dev` → `staging` → `production`

### Story 1.1 — ממשק עברית RTL מלא

**בתור** כל משתמש במערכת,
**אני רוצה** שכל הממשק יוצג בעברית מימין לשמאל,
**כדי ש**-השימוש יהיה טבעי לדוברי עברית.

**קריטריוני קבלה:**
- כל הטקסט בממשק הפנימי בעברית RTL
- שדות קלט ותוויות מיושרים לימין
- מונחי אנגלית (WhatsApp, ERP, API) מוצגים נכון בתוך זרימת RTL
- ממשק הלקוח החיצוני (קישורים חד-פעמיים) בעברית RTL
- `dir="rtl"` ו-`lang="he"` מוגדרים ברמת ה-`<html>` root

**NFRs:** NFR9, NFR10

### Story 1.3 — מערכת אימות משתמשים (Authentication)

**בתור** כל עובד ב-S.B.A.,
**אני רוצה** להיכנס למערכת עם שם משתמש וסיסמה,
**כדי ש**-גישה לנתונים תהיה מאובטחת ומזוהה.

**קריטריוני קבלה:**
- דף כניסה עם שדות שם משתמש + סיסמה בעברית RTL
- כניסה מוצלחת יוצרת session מאובטח (Supabase Auth JWT)
- ניסיון גישה ללא session מפנה לדף הכניסה
- Session פג לאחר 8 שעות חוסר פעילות — המשתמש מקבל הודעה ומופנה לכניסה מחדש
- סיסמה מוצפנת — לא נשמרת ב-plain text
- כישלון כניסה מחזיר הודעת שגיאה כללית (לא מפרט אם שם המשתמש קיים)
- כניסה מוצלחת/כושלת נרשמת ב-Audit Log עם IP ותאריך

**NFRs:** NFR1

> **הערה ארכיטקטורית:** אימות ממומש דרך Supabase Auth. זוהי תשתית הכרחית לפני כל Epic אחר.

### Story 1.4 — מערכת הרשאות לפי 4 תפקידים (RBAC)

**בתור** מנהלת המערכת,
**אני רוצה** שכל עובד יראה ויוכל לבצע רק את מה שמותר לתפקידו,
**כדי ש**-מידע רגיש לא ייחשף לאנשים שאינם מורשים.

**קריטריוני קבלה:**

| תפקיד | סוג כניסה | הרשאות |
|--------|-----------|---------|
| מתאמת החזרות (×2) | שם משתמש + סיסמה | פתיחה, עריכה, העלאה, שליחה |
| מנהלת לוגיסטיקה | שם משתמש + סיסמה | הכל + סגירת תיקים + דוחות |
| מנהלת מפעל | שם משתמש + סיסמה | צפייה בלבד — ללא עריכה |
| לקוח חיצוני | קישור חד-פעמי בלבד | פעולות ספציפיות לפי סוג הקישור |

- גישה לא מורשית (endpoint או UI) מחזירה שגיאה 403 ומתועדת ב-Audit Log
- Row Level Security (RLS) מופעל ומוגדר על כל טבלאות Supabase (ראה Story 1.10)
- ניתן להוסיף תפקיד חדש ללא שינוי ארכיטקטורה — הרשאות מוגדרות בטבלת תפקידים

**NFRs:** NFR1

### Story 1.5 — Audit Log אוטומטי

**בתור** מנהלת לוגיסטיקה,
**אני רוצה** שכל פעולה במערכת תירשם אוטומטית,
**כדי ש**-בסכסוך עם לקוח אוכל להוכיח כל שלב בתהליך.

**קריטריוני קבלה:**
- כל יצירה / עדכון / סגירה / העלאה / מחיקה נרשמת עם: מזהה ייחודי, תאריך, שעה, זהות המבצע
- כניסת לקוח חיצוני דרך קישור נרשמת עם IP ותאריך
- Audit Log מיושם כטבלת `audit_log` ב-PostgreSQL — append-only, ללא UPDATE/DELETE
- מנהלת לוגיסטיקה יכולה לצפות ב-Log מסונן לפי תיק
- פעולות RBAC כושלות (ניסיון גישה לא מורשית) נרשמות

**schema טבלת audit_log:**

| עמודה | טיפוס | הסבר |
|-------|--------|-------|
| `id` | UUID | מזהה ייחודי |
| `case_id` | UUID nullable | תיק מקושר (null לפעולות מערכת) |
| `action` | TEXT | סוג הפעולה (CREATE_CASE, UPDATE_STATUS, UPLOAD_DOC, ...) |
| `performed_by` | UUID nullable | מזהה משתמש (null לפעולות לקוח חיצוני) |
| `performed_by_role` | TEXT | תפקיד המבצע |
| `ip_address` | TEXT | כתובת IP |
| `details` | JSONB | פרטים נוספים (ערכים לפני/אחרי שינוי) |
| `performed_at` | TIMESTAMPTZ | תאריך ושעה מדויקים |

**NFRs:** NFR4

### Story 1.6 — הצפנת מסמכים, גיבוי ועמידות

**בתור** מנהלת מפעל,
**אני רוצה** שכל הנתונים יהיו מוגנים ונגישים תמיד,
**כדי ש**-לא יהיה אובדן מידע ולא ייחשף מידע רגיש.

**קריטריוני קבלה:**
- כל הקבצים ב-Supabase Storage מוצפנים at-rest
- גיבוי אוטומטי מלא אחת ל-24 שעות
- נתונים שמורים ב-3 עותקים פיזיים במיקומים שונים (Supabase מבטיח זאת)
- זמינות מערכת כוללת: SLA 99.9%+ (Supabase Cloud)
- Supabase Storage זמינות: 99.999% (כפי שמוגדר בארכיטקטורה v1.0, החלטה 4)
- זמן תגובה לפעולות API רגילות (CRUD): עד 3 שניות; חיפוש — עד 5 שניות (Story 5.1)

**NFRs:** NFR5, NFR6, NFR8

> **הבחנת SLA (v1.3):** ארכיטקטורה v1.0 מציינת 99.999% לרכיב ה-Storage בלבד. זמינות המערכת הכוללת (Supabase Cloud SLA) היא 99.9%+. שתי הדרישות תקפות בתחומיהן — אין סתירה.

### Story 1.7 — תשתית קישורים חד-פעמיים

**בתור** מתאמת החזרות,
**אני רוצה** שהמערכת תוכל לייצר קישורים חד-פעמיים לפעולות לקוח,
**כדי ש**-לקוחות חיצוניים יוכלו לבצע פעולות ספציפיות בבטחה — ללא חשבון.

**קריטריוני קבלה:**
- מנגנון ייצור token ייחודי לכל קישור (UUID v4)
- כל קישור תקף למשך 24 שעות מרגע היצירה
- קישור שנוצל (single-use) נפסל אוטומטית לאחר שימוש ראשון
- קישור שפג תוקפו מחזיר הודעת שגיאה ברורה (ראה Story 6.7)
- סוג הקישור מקודד ב-token — מגביל לפעולה הספציפית בלבד
- ניסיון שימוש בקישור פסול/פג תוקף נרשם ב-Audit Log עם IP ותאריך
- הלוגיקה ממומשת במודול `auth` — Supabase Edge Function

**schema טבלת one_time_tokens:**

| עמודה | טיפוס | הסבר |
|-------|--------|-------|
| `id` | UUID | מזהה ייחודי |
| `token` | UUID | הטוקן עצמו (נשלח בקישור) — UNIQUE |
| `case_id` | UUID | תיק מקושר |
| `action_type` | TEXT | `signature` / `coordination` / `upload` / `cancellation` |
| `expires_at` | TIMESTAMPTZ | תוקף: created_at + 24h |
| `used_at` | TIMESTAMPTZ nullable | null = טרם נוצל; מלא = נוצל |
| `created_by` | UUID | מזהה מתאמת שיצרה |
| `created_at` | TIMESTAMPTZ | זמן יצירה |
| `ip_used` | TEXT nullable | IP ממנו נוצל |

> **אכיפת תוקף:** תוקף נבדק בעת גישה ב-Edge Function — `expires_at < NOW() OR used_at IS NOT NULL` → דחייה. אין צורך ב-cron job לניקוי; פגי תוקף נחסמים בלוגיקה.

**NFRs:** NFR2, NFR3

### Story 1.8 — סביבות פיתוח ו-CI/CD

**בתור** צוות הפיתוח,
**אני רוצה** שתהיה הפרדה ברורה בין סביבות dev / staging / production,
**כדי ש**-שינויים לא יעברו ישירות לייצור ולא יפגעו במשתמשים אמיתיים.

**קריטריוני קבלה:**
- 3 סביבות מוקמות: `dev` (פיתוח), `staging` (בדיקות), `production` (ייצור)
- לכל סביבה: Supabase project נפרד + Vercel deployment נפרד
- משתני סביבה (API keys, DB connection strings) מנוהלים דרך Vercel env vars — לא hardcoded בקוד
- Pipeline דרך **GitHub Actions**: push לענף `main` → deploy אוטומטי ל-`staging`; deploy ל-`production` דורש אישור ידני ב-GitHub
- שלבי ה-pipeline: lint → type-check → build → deploy
- DB migrations מנוהלות ב-version control (תיקיית `supabase/migrations`)
- ה-schema הראשוני (ראה Story 1.10) נוצר ומאומת ב-`dev` לפני פיתוח Epic 2

**NFRs:** NFR6, NFR8

> **נימוק v1.2:** ארכיטקטורה v1.0 (החלטה 7) מגדירה במפורש 3 סביבות ומדגישה ש"שינוי לא עובר ישירות לייצור".
> **עדכון v1.3:** נוסף ציון מפורש של GitHub Actions כמנוע ה-CI/CD ושלבי ה-pipeline. הגדרת ה-schema הוצאה לסיפור ייעודי 1.10.

### Story 1.9 — הקמת scaffold פרויקט React ומבנה מודולרי [חדש v1.3]

**בתור** צוות הפיתוח,
**אני רוצה** שפרויקט ה-React יוקם עם כל התלויות ומבנה תיקיות לפי Modular Monolith,
**כדי ש**-כל מפתח יוכל להתחיל לפתח מודול ספציפי ללא חסמים תשתיתיים.

**קריטריוני קבלה:**
- פרויקט מאותחל עם: Vite + React + TypeScript
- מותקן ומוגדר: Tailwind CSS + shadcn/ui + RTL (כולל `dir="rtl"` ב-root)
- מותקן: React Router v6 עם routing ראשוני (login, dashboard, case/:id, external/:token)
- מותקן ומוגדר: Supabase JS client (`@supabase/supabase-js`) עם environment variable
- מבנה תיקיות לפי ארכיטקטורה v1.0, החלטה 2:

```
src/
├── modules/
│   ├── auth/          # כניסה, הרשאות, קישורים חד-פעמיים
│   ├── cases/         # פתיחה, עריכה, סגירת תיקים
│   ├── customers/     # לקוחות, פרויקטים, אתרים
│   ├── documents/     # תעודות, תמונות, נוהל חתום
│   ├── coordination/  # תאריכי החזרה, משאיות
│   ├── notifications/ # הודעות ותזמון
│   ├── whatsapp/      # בוט — מבודד לחלוטין
│   └── search/        # חיפוש גלובלי
├── shared/
│   ├── components/    # רכיבים משותפים (Button, Table, Modal...)
│   ├── hooks/         # hooks כלליים
│   └── utils/         # פונקציות עזר
└── app/               # Router, providers, layout
```

- ספריית חתימה דיגיטלית מותקנת ומאומתת: `react-signature-canvas` (ראה ארכיטקטורה v1.0, החלטה 8) — component לדוגמה עם Canvas עובד ב-mobile
- מותקן: eslint + prettier עם config לפרויקט
- הפרויקט בונה (`npm run build`) ללא שגיאות ומתפרס ל-Vercel `dev`

**NFRs:** NFR9, NFR10, NFR11

> **נימוק v1.3:** ארכיטקטורה v1.0 (החלטות 2, 6, 8) מגדירה את ה-stack ואת מבנה המודולים. ללא סיפור זה אין אבן-יסוד לפיתוח — כל Epic שמגיע אחר כך תלוי בתשתית זו. ספריית החתימה נדרשת ב-Epic 6 (Story 6.2) ועדיף לאמת שהיא עובדת ב-mobile כבר בשלב התשתית.

### Story 1.10 — schema ראשוני של מסד הנתונים [חדש v1.3]

**בתור** צוות הפיתוח,
**אני רוצה** שטבלאות הליבה של מסד הנתונים יוגדרו וייווצרו ב-Supabase,
**כדי ש**-Epic 2 יוכל להתחיל בפיתוח בלי לחכות להחלטות schema.

**קריטריוני קבלה:**
- כל הטבלאות שלהלן נוצרות בקובץ migration ב-`supabase/migrations/`
- RLS מופעל (`ALTER TABLE ... ENABLE ROW LEVEL SECURITY`) על כל הטבלאות — deny by default
- טבלאות נוצרות ב-`dev` תחילה, לאחר אישור — מועברות ל-`staging`

**טבלאות ליבה (Epic 1):**

| טבלה | תיאור | תלויות |
|------|--------|---------|
| `customers` | לקוחות (שם, טלפון) | — |
| `projects` | פרויקטים (שם, customer_id) | customers |
| `sites` | אתרים (שם, project_id, כתובת) | projects |
| `equipment_types` | סוגי ציוד (שם, קטגוריה) | — |
| `cases` | תיקי החזרה (ראה שדות) | customers, projects, sites, equipment_types |
| `audit_log` | יומן פעולות (ראה Story 1.5) | cases (nullable) |
| `one_time_tokens` | קישורים חד-פעמיים (ראה Story 1.7) | cases |

**שדות עיקריים של טבלת `cases`:**

| עמודה | טיפוס |
|-------|--------|

### Story 2.3 — עדכון סטטוס תיק

### Story 2.4 — סגירת תיק

**קריטריוני קבלה:**
